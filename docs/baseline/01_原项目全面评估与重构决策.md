# 01 · 原项目全面评估与重构决策

> 评估对象：`项目改进备选方案（毕业生就业管理系统)/GraduateManagementCPP/`
> 基线：v1.5 · 评估日期：2026-11-12　方法：源码逐文件审计 + 数据库实测 + 课程条款映射 + 加权决策分析
> 结论摘要：**建议全量重构（推倒实现层、保留需求层），并以 AI 能力层作为新的设计主轴。**

---

## 1. 评估方法与口径

本评估刻意避免"看起来很旧所以该重写"这类主观判断，采用四步可复核流程：

1. **事实盘点**：对 `src/`、`include/`、`static/`、`CMakeLists.txt`、`build/data/graduate.db` 做静态扫描与 SQL 实测，统计基于源目录（不重复计 build/static），行数统一为 .NET ReadAllLines，文件大小按字节；数据库以 sqlite_master 与逐表 count(*) 复核。示例 grep/find 命令只说明原始统计意图，在 Windows 用 rg/PowerShell 等价复核。
2. **条款建模**：把课程验收条款拆成可验证的设计约束（见 02 §1、06 §1），再逐条对照原项目是否留有证据。
3. **缺陷定级**：按「对验收结果的伤害」而非「代码洁癖」排序，P0 = 演示失败或合规风险，P1 = 明确扣分，P2 = 工程质量债。
4. **方案决策**：对三个候选路线按同一组加权指标打分， sensitivity check（改变权重后结论是否翻转）。

> 说明：下文评分表是**课程评分视角的自评量表**，权重由项目自行设定（课程未给出数值权重），分值是"证据充分程度"的等级判断，不是客观测量值；其价值在于让取舍可讨论、可追溯，而非伪装精确。

### 2.1 对上一版方案的两处更正

上一轮产出的《毕业生就业管理系统_升级改造方向全景方案.html》整体结论有参考价值，但本次复核发现两处需要更正，后续文档一律以本次实测为准：

| 项 | 上一版表述 | 本次实测 | 处理 |
|---|---|---|---|
| 路由数 | 108 条 | **88 条**（未去重亦为 88，无重复注册） | 全文改用 88；不影响"CRUD 数量堆砌"的判断，但报告里写错数字会被质疑 |
| 技术路线 | 推荐"Vue SPA + Repository 双模（LocalAdapter / HttpAdapter 对接重构后的 C++ REST）"，主张保留并复用自研服务器资产 | 见 §7：**在 AI 主线下该建议应推翻** | 双模适配层不再进入新架构；C++ 服务器降级为报告中的"协议原理对照"，不进入运行链路 |

> 更正理由不是"C++ 不好"，而是**目标函数变了**：上一版的目标函数是"最大化继承原项目资产"，本轮用户已把目标函数改为"以 AI 奠定总设计、把有限工期投入技术难度与界面美观度"。在这个目标函数下，维护一套与 AI 无关的 C++ 编译链与适配层是纯成本。

## 5. 诊断结论：三层错配

把 4 节的缺陷合并看，原项目的瓶颈不是"功能不够多"：

```
① 工程表达不足   原生 MPA 合规，但内联代码庞大、前端组件与路由证据不足
② 价值形态错配   32 张表只做登记与查询，没有一条数据变成"建议、预测、解释、预警"
③ 工程形态错配   演示级工程（exe + CDN + 无测试）却承担"应用价值"叙事
```

因此正确的动作是**换维度**：从「信息登记系统」→「AI 驱动的就业决策与服务平台」，而不是在 88 条 CRUD 后再加 20 条 CRUD。

### 6.2 丢弃（实现层 —— 这是"推倒"的实质）

> **C++ 自研 HTTP Server 的特殊处置**：不进入运行链路，但**保留为报告素材**。它恰好是课程大纲第 5 章「Web Application and Web Server」的活教材，可在报告"关键技术"里用一张对照表说明：原系统手写请求解析/路由匹配/CORS 预检 → 新系统由 Vue Router + Fetch 中间件 + 受限 FastAPI AI Gateway 分别承担，并解释 HTTP 状态码、REST 语义、SSE 流式与缓存。这样既彻底甩掉编译依赖，又不浪费原有技术积累。

## 7. 三案加权决策矩阵

| 方案 | 描述 | 继承性 | 合规 | 技术难度 | 界面上限 | 工期可控 | 演示稳定 | 加权分 |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| **A 渐进改造** | 保留 C++ + MPA，修 bug、加几个 AI 页面 | 5 | 5 | 2 | 2 | 4 | 2 | **3.16** |
| **B 上一版方案** | Vue SPA + Repository 双模，保留并重构 C++ REST | 5 | 5 | 3 | 5 | 2 | 4 | **4.02** |
| **C 全量重构 · AI 优先（推荐）** | 需求层继承、实现层重做；Vue 3 SPA + IndexedDB + 三态 AI Provider；Python FastAPI 仅作AI Gateway（v1.5必做接入、按需运行） | 3 | 5 | 5 | 5 | 4 | 5 | **4.67** |

本表为内部决策辅助：权重不是教师给定，收益分是设计估计而非已运行证据。A/B/C 均合规；“重新选择 C”不以否定原系统合规性为前提。

权重：继承性 0.10 / 合规 0.20 / 技术难度 0.22 / 界面上限 0.20 / 工期可控 0.13 / 演示稳定 0.15（合计 1.00）。
分值 1–5；加权分按 `Σ(权重×分值)` 复算。C 在"继承性"上低于 A/B，是这次重构唯一要付的代价。

**敏感性检验（如实报告，不做有利裁剪）**：只提高"继承性"权重 `k`、其余五项按原比例等比压缩，结果如下：

| 继承性权重 k | A | B | C | 领先方案 |
|---:|---:|---:|---:|---|
| 0.10（基准） | 3.16 | 4.02 | **4.67** | C |
| 0.20 | 3.36 | 4.13 | **4.48** | C |
| 0.30 | 3.57 | 4.24 | **4.30** | C（优势已很小） |
| 0.32 | 3.61 | 4.26 | **4.26** | 临界 |
| 0.35 | 3.67 | **4.29** | 4.21 | B |

**B/C 交叉点约 k = 0.321**：结论依赖“实现资产继承性”的主观权重，而非无条件客观最优。当前已约定保留业务方向、重写实现，因此维持 C；若新增必须复用 C++ 代码的硬约束，须重新评审，不得自动改回 B 或引入业务 HttpAdapter。

### 7.1 为什么推翻上一版的"双模保留 C++"

1. **目标函数变了**：本轮以 AI 奠定总设计，工期应集中在 AI 能力、自研内核与界面，而非适配层与 C++ 契约修复。
2. **双模是纯成本**：`LocalAdapter` 与 `HttpAdapter` 要维护两份数据映射；而原 C++ 的 88 条 API 中，AI 功能一条都用不上。
3. **安全债无法沿用**：P0-2/3/4 属于认证模型缺陷，重构 C++ 鉴权的工作量大于在新系统中重新设计。
4. **C++ 的教学价值可以用文档兑现**：报告里讲清 HTTP 原理即可拿到大纲第 5 章的分数，不必让它承担运行时。
5. **用户已明确授权**："完全可以全部推倒重来""后端可以采用更合理的语言，不用局限于原始的 C++"。

### 7.2 为什么 Python 后端只做"可选"而不是"必需"

课程验收条款限定的是**前端实现技术**，并未要求必须有独立后端；但引入后端可以解决真实 AI 调用的三个硬问题（API Key 不能放前端、浏览器跨域、SSE 流式与限流审计）。所以定位为：

- **默认态（答辩 / 提交包）**：纯静态 `dist/` + 浏览器 IndexedDB + REPLAY/RULE 态 AI，**零业务后端、零外网、零密钥**；仍需预装 Node 与本机静态 HTTP 服务（14），已启用 MVP 可演示；
- **真实AI态（v1.5正式交付项、运行时可关闭）**：统一入口启动 `Python 3 + FastAPI` 网关；首适配DeepSeek，用户在网关专用配置文件填Key，经配对/连接测试/显式外发确认后切LIVE。密钥不写源码或前端，详见15。

这样既顺应"后端可以用 Python"的设想，又不让演示稳定性被网络与账号绑架。
